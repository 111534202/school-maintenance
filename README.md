# 學校設備維保電子化系統

校園設備的自助除錯、報修、派工、維修與驗收，以及教室、設備、用戶等主檔管理。
以 Laravel 13（PHP 8.4）、MySQL 8.4、Bootstrap 5.3 與 Chart.js 4 開發。

> 四位組員使用同一個 Git Repository，各自使用本機的 MySQL，資料表結構只透過 migration 同步、測試資料只透過 seeder 同步。
> 不要把 `.env`、`vendor`、`node_modules` 或真實密碼提交到 Git。

## 第一次安裝

需要：PHP 8.4（含 pdo_mysql）、Composer 2、MySQL 8.4。

```bash
composer install
cp .env.example .env
php artisan key:generate
```

1. 在本機 MySQL 建立資料庫 `school_maintenance`（字元集 utf8mb4）。
2. 編輯 `.env`，在 `DB_PASSWORD` 填入自己的 MySQL 密碼（`.env` 不會被提交）。
3. 建立資料表並寫入示範資料：

```bash
php artisan migrate:fresh --seed
```

4. 啟動網站，開啟 <http://127.0.0.1:8000>：

```bash
php artisan serve --host=127.0.0.1 --port=8000
```

`migrate:fresh` 會**清空整個資料庫**再重建，只在本機開發使用。已經有資料、只想套用新的資料表變更時，用 `php artisan migrate`。

## 示範帳號

登入頁用「帳號名稱」或 Email 登入。示範資料裡所有帳號的密碼都是 `password`（只是示範用，正式使用前務必更換）。

| 帳號名稱 | 身分 | 能做的事 |
|---|---|---|
| `admin` | 系統管理員 | 全部權限 |
| `it_manager` | 資訊組主管 | 教室／設備／設備類別主檔、派工、查看操作紀錄、管理知識庫、接收派工通知副本；保養模組全部功能（含 AI 預防保養）、零件庫存、空間預約管理 |
| `repairer` | 維修人員 | 提出報修；處理「指派給自己」的案件（示範資料裡沒有指派給他的案件，看板是空的）；查看保養資料並回報保養結果 |
| `teacher` | 教師 | 提出報修；驗收「自己報修」的案件（示範案件除了保養 NG 轉入的那張，報修人都是這個帳號） |
| `executive` | 主管 | 提出報修、派工、看全部案件；驗收自己報修的案件；查看保養資料 |

要看完整的維修流程，可以用 `admin` 登入，或到報修單詳細頁把案件派給維修人員。

## 教室、設備、報修單的連動顯示

- **教室主檔**列表每間教室顯示「設備數、異常設備數、進行中工單數」；有異常設備的教室整列標紅，核心設備異常的另外加「核心」徽章，可用「設備狀況」篩選只看有異常設備的教室。
- 點「設備數」或「異常設備」跳到**設備主檔**（自動帶好教室，異常設備會只列出異常的）；點「進行中工單」跳到**報修看板**（自動帶好教室）。
- **設備主檔**每台設備顯示進行中報修單數，點了跳到報修看板（只看這台設備）；狀態徽章依狀態上色。
- 「異常設備」= 狀態是維修中、已淘汰或停用，定義只有一份（`DeviceStatusService::PROBLEM_STATUSES`），教室主檔、設備主檔與主控台都用它。
- 「進行中工單」是透過設備串到報修單（報修單的 `device_id`），不含已結案；沒有綁定設備、只用文字描述的報修單不會算進教室。數字只統計這位用戶看得到的案件。

## 權限與資料範圍

- 每個身分可以做哪些事，由「身分主檔」勾選的權限決定（權限清單在 `app/Support/PermissionCatalog.php`）；系統管理員永遠擁有全部權限。
- 報修單另外有「這一張單是不是你的」的限制（`app/Policies/RepairRequestPolicy.php`）：
  能派工的人與管理員看全部；其他人只看自己報修或被指派的案件；
  只有被指派的維修人員能開始處理與填維修紀錄；只有報修人能驗收或退回。
  這個資料範圍規則依規格書的角色說明整理，**細部規則仍列在待確認事項**，要調整只需要改這一個檔案。
- 知識庫文章有「上架／未上架」：未上架（草稿）只有擁有「管理知識庫」權限的人看得到，其他人列表看不到、直接開網址是 404。
- 報修單的「開始處理」只能用在「已派工」的案件；待驗收的案件要退回處理中，只能由報修人走「驗收退回」（必填原因）。
- 零件庫存由 `parts.manage` 權限控制，空間預約的審核由 `reservations.manage` 控制，都在身分主檔勾選；保養模組有 `maintenance.*` 與 `ai-maintenance.manage` 四項。
- 附件（照片、影片）存在私有磁碟，只能透過網站下載，並套用同樣的檢視權限。
- 帳號被停用後，下一個請求就會被強制登出；登入失敗太多次會暫時鎖定（見 `LoginController`）。

## 升級已經建好的資料庫

拉到新版程式後執行一次 `php artisan migrate`（只新增資料表與補權限，不會清資料）。
示範資料（保養項目、零件等）只有 `php artisan migrate:fresh --seed` 才會寫入，這個指令會清空資料庫，已有資料時不要用。

## 資料庫命名規則與名稱清單

- **`docs/資料庫命名規範與資料字典.md`**（唯一一份）：取名邏輯（12 條規則與取新欄位名稱的步驟）、固定詞彙表、代碼值清單、例外與理由、每張資料表的正規化檢查結果、資料表一覽、ERD、**每個資料表與欄位的完整名稱清單（含型態、必填、唯一、外鍵、說明）**，以及和規格書第 8 章的差異。
- 這份文件是從實際資料庫自動產生的：改了資料表或欄位後執行 `php artisan docs:schema` 更新；`php artisan docs:schema --check` 只檢查是不是最新（測試會跑，過期就失敗）。
- 新增資料表或欄位請走 migration，並跑 `php artisan test`：`DatabaseNamingConventionTest` 檢查名稱合不合規則、`DatabaseNormalizationTest` 檢查參照欄位有沒有外鍵與主鍵是不是 `id`。

重點規則：主鍵一律 `id`；指向其他資料表叫 `<資料表單數>_id` 並有外鍵；指向「人」只有 `requester_id`／`manager_id`／`assigned_to`／`*_by`；布林 `is_`／`has_`；時間 `_at`、日期 `_date`；狀態 `status`；備註單數 `note`；業務代碼 `<實體>_code`；能由別的欄位推出來的不另存、一個欄位只放一個值（身分勾選的權限因此拆成 `role_permissions`）。

## 手機版的「洋蔥式」版面

手機（寬度小於 768px）上，頁面一層一層看，不用左右拖表格、也不用一直往下滑；桌面版完全不變：

- 列表的表格變成卡片，只顯示標題、重點欄位與操作按鈕，其餘欄位按「詳情」才展開。
- 篩選列收成一顆「篩選」按鈕（已套用幾個條件會顯示數字），點開後欄位上下排列。
- 詳細頁與長表單的各個區塊可以收合，預設只展開第一個；必填欄位或錯誤訊息所在的區塊會自動展開。
- 做法與調整方式見 `public/css/onion.css`、`public/js/onion.js` 檔頭；表格要讓哪些欄位留在第一層，在 `<table>` 加 `data-onion-primary="欄位索引"`。

## 常用指令

```bash
php artisan test                      # 執行全部自動化測試（使用記憶體中的 SQLite，不會動到本機資料庫）
php artisan migrate:fresh --seed      # 重建資料庫並寫入示範資料（會清空資料）
php artisan view:clear                # 清除畫面快取（改了畫面卻沒更新時用）
```

## 其他注意事項

- 畫面樣式（Bootstrap、圖示）與圖表（Chart.js）、相機掃描函式庫是從網路 CDN 載入，沒有網路時畫面會沒有樣式與圖表。
- 派工通知信目前寫入 `storage/logs/laravel.log`，不會真的寄出（`.env` 的 `MAIL_MAILER=log`）；要寄信只需要改 `.env`。
- 語言切換選單預設隱藏；中英文翻譯都在 `lang/`，要開放把 `.env` 的 `APP_LOCALE_SWITCHER` 設成 `true`。
- 系統時區預設是台北（`APP_TIMEZONE=Asia/Taipei`）。
- 設備狀態與報修流程的自動連動規則（案件處理中是否自動把設備標成維修中）尚未確認，目前沒有串接，見 `docs/待確認/`。
