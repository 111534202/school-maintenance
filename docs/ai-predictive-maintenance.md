# AI 預測性維護說明文件

> 負責人：王佑恩（111534234）｜模組：定期保養、AI 預測性維護、設備履歷
> 本文件說明「AI 預防保養」功能的資料來源、輸入、計算方式、門檻、限制，以及 Demo 資料的真實性聲明，可直接用於口試與成果書。

## 1. 功能定位（先講清楚它是什麼、不是什麼）

本系統的「AI」是**規則式（rule-based）風險評分**，不是機器學習、也沒有訓練任何模型。
做法是：依設備過去的保養紀錄，用一組固定、公開的規則算出 0～1 的風險分數；分數達到門檻就提出「預防保養候選」，經主管核准後才建立 AI 來源的保養工單。

選擇規則式的原因：

- 學校設備的保養歷史筆數少（每台設備每月一筆），資料量不足以訓練可靠的機器學習模型。
- 規則式每一步都能被檢查與解釋（評分明細會逐項顯示），口試與驗收時能直接說明「為什麼是這個分數」。
- 評分邏輯集中在單一服務類別，之後若資料足夠，可以換成其他演算法，而不用改畫面與流程（見第 9 節）。

## 2. 資料來源

| 資料 | 來源資料表 | 用途 |
| --- | --- | --- |
| 保養工單 | `maintenance_orders` | 找出該設備已完成的工單 |
| 保養結果 | `maintenance_results` | 每次保養的 OK／NG 與執行時間 |
| 設備 | `devices`（林政寬模組，唯讀） | 只掃描狀態為「正常」的設備 |

目前**沒有納入**報修／維修歷史：該模組（彭仕衡）尚未併入 `develop`，評分結果與畫面上都會註明「報修／維修歷史尚未串接」。併入後可新增一個評分項目，不需要修改介面。

## 3. 輸入特徵

由 `MaintenanceFeatureExtractor` 從上述資料整理出來，主要有：

- `result_sequence`：依執行時間由舊到新的 OK／NG 序列
- `ng_count`、`ok_count`、`ng_rate`：NG／OK 次數與比例
- `last_maintenance_at`、`days_since_last_maintenance`：最近一次保養時間與距今天數
- `repair_data_available`：目前固定為 false（報修資料未串接）

## 4. 計算方式

風險分數（0～1）由三個項目加權相加：

```
風險分數 = 0.5 × 最近 N 筆保養的 NG 比例
         + 0.3 × min(結尾連續 NG 次數, 3) ÷ 3
         + 0.2 × 保養逾期程度
```

- 最近 N 筆：預設 N = 6，可在設定頁調整。
- 結尾連續 NG：從最新一筆往前數，連續幾次是 NG，最多算 3 次。
- 保養逾期程度：距上次保養 45 天以內為 0，90 天以上為 1，中間線性增加。
- 若已回報結果的保養紀錄少於最少筆數（預設 4 筆），**不評分**（資料不足），也不會提出候選。
- 權重（0.5／0.3／0.2）、45／90 天、連續 NG 上限 3，集中寫在 `RuleBasedPredictionService` 的常數中。

**計算範例**（設備 DEV-AI-002，歷史由舊到新為 OK、NG、OK、NG、NG、NG）：

| 項目 | 原始值 | 權重 | 貢獻分數 |
| --- | --- | --- | --- |
| 最近 6 筆 NG 比例（4／6） | 0.667 | 0.5 | 0.333 |
| 結尾連續 NG（3 次，滿分） | 1.000 | 0.3 | 0.300 |
| 保養逾期程度（距上次 32 天） | 0.000 | 0.2 | 0.000 |
| **風險分數** | | | **0.633** |

同樣的保養歷史、同一天計算，結果一定相同（可重現）。

## 5. 門檻與可調參數

管理員（admin／資訊組主管）可在「AI 預防保養設定」頁調整，存放於 `ai_settings` 資料表；沒有設定時使用預設值。

| 參數 | 預設值 | 說明 |
| --- | --- | --- |
| 風險分數門檻 | 0.5 | 分數大於等於此值就提出候選 |
| 最少保養紀錄筆數 | 4 | 低於此筆數視為資料不足 |
| 評分最近幾筆 | 6 | 計算 NG 比例的視窗大小 |
| 去重天數 | 14 | 見第 7 節 |
| 是否需主管審核 | 是 | 否則達門檻直接建立 AI 工單 |

以上預設值皆為**工程實作決定，待全組確認**。

## 6. 流程

1. 每日 02:00 自動掃描（也可在候選頁按「立即掃描設備風險」，或執行 `php artisan ai:scan-preventive`）。
2. 對每台「正常」設備評分；資料不足、未達門檻、判定重複者略過。
3. 達門檻且不重複：
   - 需審核（預設）：產生「待審核」候選，保留當下的分數、門檻、評分明細。
   - 不需審核：直接建立 AI 來源的保養工單，並留一筆「自動建單」候選當紀錄。
4. 主管在候選頁「核准建單」或「駁回」。核准時會**再檢查一次重複**（候選產生後可能已有人建立工單），重複則不建單並標記「重複未建單」。
5. AI 工單與一般工單一樣走「回報 OK／NG」流程；NG 會標記待轉報修。
6. 掃描、核准、駁回、設定變更都會寫入共用操作紀錄（Audit Log）。

## 7. 去重規則

同一台設備符合下列任一條件，就不提出（或不建立）AI 預防保養：

1. 已有未完成（待處理／進行中）的保養工單，且排定日在「今天 + 去重天數」以內（含已逾期或未排日期）。
2. 已有一筆待審核的候選（重複掃描不會疊加）。
3. 去重天數內已建立過 AI 來源的工單。
4. 去重天數內剛被駁回過同一台設備的候選。

## 8. Demo 資料（重要：模擬資料聲明）

Demo 使用的保養歷史是由 `AiDemoDataSeeder` **模擬產生**的，用來展示規則與流程，**不是學校真實的多年保養資料**，也沒有宣稱具備統計上的預測準確度。執行 `php artisan migrate:fresh --seed` 會得到完全相同的結果。

| 設備 | 保養歷史（舊→新） | 風險分數 | 預期結果 |
| --- | --- | --- | --- |
| DEV-0001 | OK OK OK OK NG OK | 0.083 | 未達門檻 |
| DEV-AI-001 | OK OK NG OK OK OK | 0.083 | 未達門檻 |
| DEV-AI-002 | OK NG OK NG NG NG | 0.633 | 達門檻，產生待審核候選 |
| DEV-AI-003 | OK OK OK（僅 3 筆） | — | 資料不足，不評分 |
| DEV-AI-004 | OK OK OK NG NG NG | 0.550 | 達門檻，但已有 7 天後到期的定期工單，去重略過 |

這張表由自動測試（`tests/Feature/Ai/SeededAiDemoTest.php`）鎖定，每次測試都會檢查，結果不一致測試就會失敗。

## 9. 限制與誠實說明

- 只是規則式評分，**不能預測故障何時發生**，只是把「最近常異常、連續異常、很久沒保養」的設備排到前面提醒人工處理。
- 評分只用保養紀錄；沒有報修／維修、使用時數、環境、設備年份等資料。
- 資料量小，分數會受單筆結果影響；門檻與權重沒有用真實故障資料校準，是工程判斷。
- 規則與預設值尚待全組正式確認。
- 若日後累積足夠資料，可以新增另一個實作 `PredictionServiceInterface` 的類別（例如機器學習模型），並在 `AppServiceProvider` 改綁定；候選、審核、去重、設備履歷畫面都不用改。

## 10. 如何重現與驗證

```
php artisan migrate:fresh --seed     # 建出可重現的 Demo 資料
php artisan ai:scan-preventive       # 掃描並列出每台設備的分數與結果
php artisan ai:device-features DEV-AI-002   # 看單一設備的特徵與評分明細（JSON）
php artisan test                     # 全部自動測試
```

畫面：登入後左側「AI 預防保養」（候選審核、設定）與「設備履歷」（單台設備的風險評估與候選紀錄）。

## 11. 口試可能被問的問題

- **這是真的 AI 嗎？** 是規則式風險評分，不是機器學習；我們誠實標示，且評分明細可逐項檢查。
- **為什麼不用機器學習？** 資料筆數太少，訓練出來的模型不可靠；規則式可解釋、可驗證，也能當作日後換模型的介面。
- **分數怎麼來的？** 見第 4 節公式與範例。
- **門檻怎麼決定？** 預設 0.5 是工程決定，管理員可調整，尚未用真實故障資料校準。
- **Demo 資料是真的嗎？** 不是，是模擬歷史，目的是展示規則與流程。
- **會不會重複開工單？** 有去重（第 7 節），掃描與核准兩個時間點都會檢查。
- **一定要主管審核嗎？** 預設要；可設定改為直接建立。
