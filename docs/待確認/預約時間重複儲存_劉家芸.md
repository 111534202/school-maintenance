## 1. 白話說明

一張「教室預約申請」現在有**兩個地方**記錄使用時間：

1. **申請本身**（`classroom_reservations`）：`reservation_date`（日期）、`start_time`、`end_time`，只能記**一組**時間。
2. **時段明細**（`classroom_reservation_slots`）：每個時段各自一列，同樣有 `reservation_date`、`start_time`、`end_time`，另有節次 `period_number`。**一張申請可以有很多個時段**（例如週一第 1 節、週二第 5 節）。

劉家芸後來為了支援「一次預約多天、多節」，新增了時段明細表，但**沒有把申請本身原有的三個時間欄位拿掉**。結果同一件事（「什麼時候用教室」）被記在兩個地方：申請本身只記得其中**第一個**時段，明細表則記得全部。

打個比方：像一張會議邀請，信件標題寫了「11/8 09:00」，信裡卻列了三場會議。標題只抄了第一場，之後第一場被取消，標題也不會自己更新。

## 2. 目前程式怎麼處理這兩份

| 位置 | 做什麼 | 檔案 |
|---|---|---|
| 建立申請 | 驗證時**同時要求**頂層的日期／時間和 `slots`；寫入時把「第一個時段」複製一份存進申請本身，再把全部時段寫進明細表 | `app/Http/Controllers/ClassroomReservationController.php`（`store()`，約 119–160、225–245 行） |
| 衝突檢查（核准時） | **先**查時段明細；只有「該申請完全沒有任何時段」才退回去看申請本身的時間 | `app/Services/ReservationReviewService.php`（約 25–55 行） |
| 審核 | 申請沒有時段（舊資料）時，**先用申請本身的時間補出一個時段**，之後一律以時段審核 | `ReservationReviewService::review()`（約 85–95 行） |
| 詳細頁 | 同樣的「沒有時段就補一個」；畫面上申請本身的時間只在「沒有任何時段」時才顯示 | `ClassroomReservationController::show()`；`resources/views/reservations/show.blade.php`（`@empty` 區塊） |

結論：**程式真正採信的是時段明細**；申請本身的三個時間欄位，實質上只剩「第一個時段的複本」和「舊資料相容」兩個用途。

## 3. 實際重現（2026-11-05，以拋棄式測試驗證，驗證完已刪除）

步驟：教師送出一張申請，內含兩個時段（11/8 09:00–10:00、11/9 13:00–14:00）；管理者審核時**拒絕第一個、核准第二個**。

| 時間點 | 申請本身（`classroom_reservations`） | 時段明細 |
|---|---|---|
| 建立後 | 11/8 09:00–10:00 | 兩個時段 |
| 審核後 | **仍是 11/8 09:00–10:00**，狀態 `partially_approved` | 11/8 09:00–10:00 **rejected**；11/9 13:00–14:00 **approved** |

也就是：被拒絕的那個時段，仍然是「申請本身」記著的時間；真正核准可以使用教室的 11/9，在申請本身完全看不到。兩份資料已經不一致，只是目前沒有畫面去讀申請本身的時間，所以使用者看不出來。

## 4. 為什麼是問題

1. **兩份可能不一致**：沒有任何程式在時段被修改、審核時去同步申請本身的時間（上表已實測）。以後有人用 `$reservation->start_time` 做報表、通知信、行事曆匯出，會得到錯誤的時間。
2. **違反第三正規化**：申請本身的時間可以由時段明細推得（取最早的時段），卻又單獨存了一份。這與我們已經處理過的「保養計畫的設備類別可由設備推得」是同一類問題。
3. **程式要寫兩套**：「有時段」與「沒有時段（舊資料）」各一套判斷，衝突檢查、詳細頁、審核服務都要處理兩次；新增功能時容易漏掉其中一套。
4. **資料字典的判定需要更正**：自動產生的 `docs/資料庫命名規範與資料字典.md` 原本寫 `classroom_reservations`「符合 3NF」，這不正確，已改成「大致符合，但時間重複，見本文件」。
